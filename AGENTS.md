# Project guidance

## Purpose and evolution

- Build complete, enjoyable browser games and improve the internal engine that supports them. Maintain game-type foundations that coding agents can adapt from supplied themes, artwork, assets, stories and gameplay requirements. Gameplay quality and architecture quality are equal objectives. Keep a single non-published application/package; this is not a library, SDK or general-purpose engine product.
- For each new game or substantial feature, evaluate existing infrastructure, duplication, ownership and awkward abstractions. Refactor when concrete requirements make development simpler or more maintainable. Do not avoid a useful abstraction just to minimize code or wait for two identical implementations. Avoid speculative packages and architecture.
- Reuse and improve applicable shared infrastructure. Keep fundamentally different game mechanics local. Read the relevant owners and [architecture](docs/architecture.md) before changing a system; keep those documents aligned with the resulting implementation.
- Use the repository's official [arcade-lab Skill](.agents/skills/arcade-lab/SKILL.md) for creating, improving, customizing or polishing games and their engine foundations. It routes tasks to canonical guides and optional game-design references; keep its use proportional to the task.

## Ownership

- The application shell owns game selection, mounting and disposal. Game entries mount synchronously and return session cleanup, while owning their async preparation. Failed construction must release resources already created. Keep game styles scoped to their root.
- Simulation owns world state and gameplay rules. It depends on typed content, pure math and action-level input, never browser APIs, rendering, UI or audio implementations. Use typed data for content/tuning and TypeScript for behavior. Rendering, animation and audio consume state and semantic events without advancing rules.
- Browser sessions own browser APIs, listeners, scheduling and disposal. The application supplies the persistent fullscreen target; the shared host owns measurement, display-change suspension and the single frame loop; renderers own backing buffers. Input translates physical controls into actions. Reuse shared captured-button input for button-based controls; gesture translation stays local. Restart creates a fresh run. Reuse the shared page-lifetime and deferred focus bindings, supplying game-specific suspension and focus rules. Session disposal and HMR must release resources and invalidate pending async work.
- Presentation owns cameras and cosmetic state. Use one authoritative uniform world transform. Relative gestures use CSS pixels independently of camera motion. Display transitions clear held input and reset timing. Preserve the viewport-filling layout and fullscreen support.
- Physical geometry belongs in gameplay content, independently of artwork dimensions, visual scale or camera zoom. UI displays state and emits intents. Composition connects explicit owners and manages their lifetimes. Shared infrastructure contains no game content.
- Use `src/engine/` for game-independent runtime mechanisms and pure primitives, `src/engine/browser/` for their browser resource owners, and `src/common/ui/` for collection-wide menu and DOM presentation. Shared folders must not import games or the application. Keep a helper with its game if its contract knows that game's roles, state, atlas layout or renderer. Promote it only when a concrete common responsibility makes ownership or reuse simpler; neither duplication alone nor a desired folder symmetry justifies a framework.
- Keep appearance definitions, palettes, visual role mappings and renderer contracts in the owning game. Prototype is temporary and exists only until Arcade is complete; then delete its implementation and dedicated resources. Finished games start in Arcade. Show Arcade / Deluxe on title and pause menus only when both exist; hide single-choice selectors and omit missing modes. Use identical availability in every build. Follow the canonical [mode contract](docs/architecture.md#mode-contract) and [replacement/recovery workflow](docs/architecture.md#replacement-and-recovery). A theme preserves the run, gameplay content, geometry, timers and progression. Keep the working presentation until its replacement is ready, and release failed or superseded resources. Gate play on required initial artwork with retry and navigation available.

## Technologies

- Every required asset must be committed and redistributable with this public repository. Check external asset licenses before integration; reject incompatible or unclear sources and create original artwork instead. Preserve legally required third-party credits and notices alongside their assets.
- Use custom image assets for finished player characters, enemies and interactive objects in Arcade and Deluxe. Prefer complete sprites and authored animation cels with stable anchors and replaceable role mappings. Temporary primitives can establish mechanics, but do not finish actors as assembled body parts, procedural skeleton drawings, cut-up limb sprites or mesh rigs. Offline 3D artwork is welcome as pre-rendered image assets.
- Use Canvas 2D for runtime rendering in every mode. Build visual quality through authored sprites, animation cels, layered environments and composed effects. Use transforms, compositing, gradients, light stamps and bounded particles where they support the artwork. Keep expensive presentation code and images behind the owning mode's preparation boundary; extend useful local renderers without adding a generic graphics framework.
- Follow the recommended [development progression](docs/architecture.md#development-progression) in focused passes: [Prototype](docs/prototype.md) → [Arcade](docs/arcade.md) → [Deluxe](docs/deluxe.md). Arcade replaces Prototype; Deluxe is optional. Prefer one primary game-owned Canvas renderer with artwork and effect definitions. Use the corresponding guide for each stage.
- Use [AudioBits](.agents/skills/audiobits/SKILL.md) for all game sound. Reuse `src/engine/browser/audio.ts` for session-owned AudioBits lifecycle and bounded playback. Keep recipes, event mapping, cue priorities and throttle intervals local to each game; reuse shared cooldown bookkeeping. Activate synchronously in existing user gestures; pause and dispose through the session owner. Current integration status belongs in the architecture document.
- Add dependencies when their capabilities improve quality or save substantial implementation work. Avoid unnecessary wrappers and large frameworks without a concrete benefit. Do not add publishing/release infrastructure or external API stability guarantees. Add compatibility only for persisted data, an actual external consumer or an explicit requirement.

## Documentation and verification

- Keep README a short, human-facing project introduction and usage guide. Link to [CATALOG.md](CATALOG.md) for game descriptions, screenshots and controls instead of growing README with each game.
- When updating the best completed presentation’s artwork, replace the owning game’s canonical `preview.webp` screenshot with `pnpm screenshot <game-id> <capture.png>`. Follow [collection previews](docs/architecture.md#collection-previews-and-site-identity); the landing and docs share that file, and social assets are generated.
- Use CATALOG.md as the shared index for game-specific docs. Keep shared guidance independent of game names, inventories and implementation details. Document decisions where they are owned, avoid duplicating source constants or rules, and remove obsolete reports. Keep artwork docs focused on creating, adapting and integrating assets; label useful reference links as inspiration.
- Follow [documentation ownership](docs/architecture.md#documentation-ownership): link shared controls, theme contracts, lifecycle, audio and verification guidance instead of repeating it in game guides. Keep mechanics, art briefs, asset contracts, local owners and game-specific exceptions with their game; give detailed briefs one local home.
- Follow the mandatory [testing policy](#testing-policy) and [local verification commands](docs/architecture.md#local-verification).
- Do not require human playtesting sign-off or record manual-testing status, acceptance checklists or "unverified" caveats in project docs. The user tests games and reports issues as needed. Keep docs focused on usage, design and maintenance; report concrete failures when found.

## Testing policy

- Tests must earn their execution and maintenance cost by protecting a specific meaningful regression. A new feature does not automatically need a new test. Existing tests are not a precedent for expanding coverage; simplify or replace redundant scenarios instead of accumulating more.
- Default to the cheapest adequate verification: TypeScript, then small deterministic unit/invariant tests. Preserve useful fast checks for simulation ownership, collision, timing, resource cleanup, cancellation, readiness and replacement rollback. Avoid assertions about incidental artwork sizes, exact pixels or internal layouts unless they enforce a functional contract.
- Browser tests are scarce: use Chromium for startup, integration boundaries and a few critical shared lifecycle contracts. A new game normally gets one startup smoke plus focused deterministic tests for important mechanics. A smoke opens the game, checks readiness and the expected presentation, starts play, then stops. Additional browser coverage needs a specific unique integration risk that cheaper checks cannot protect.
- Test a shared contract once at the appropriate layer, with representative browser integration where needed. Do not multiply failure, input, pause/restart, fullscreen or disposal scenarios by game or presentation count. Aim for roughly 8–12 browser tests at the current collection size; exceeding that guideline requires a clear regression and cost justification in the change description.
- Do not add automated playthroughs, long simulated sessions, repeated action sequences or end-to-end interaction matrices by default. Keep deterministic mechanics checks bounded. Use gameplay and visual inspection for art quality, feel and polish without requiring human sign-off.
- Do not add routine screenshot matrices or unasserted captures to tests. Capture on demand for visual review or failure diagnosis; keep canonical collection previews separate from regression testing. Avoid arbitrary delays and extended page-clock advancement.
- Run `pnpm check` routinely. Run `pnpm check:browser` for browser integration, shared UI, presentation lifecycle, input or other browser-sensitive changes. During individual game work, prefer the relevant focused checks. Minor artwork, documentation and game-data changes do not automatically require the whole browser suite.
- Keep the existing local runners and simple fixtures. Chromium is the only automated browser. Do not add CI, device/browser matrices, coverage services or benchmark infrastructure without an explicit request. Comprehensive production verification belongs in a standalone production game's repository; Arcade Lab is an experimental workshop for rapid iteration.

Before adding a test, answer: What specific regression would it catch? Is that already covered? Would TypeScript or a fast unit test suffice? Does it genuinely need a browser? Will its execution and maintenance cost remain reasonable as games are added? **Without compelling answers, do not add it.**
